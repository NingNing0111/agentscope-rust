# Feature Specification: Agent 状态持久化（内置 JSON 文件存储 + 可插拔存储后端）

**Feature Branch**: `025-agent-state-persistence`

**Created**: 2026-08-03

**Status**: Draft

**Input**: User description: "针对agentsate，要内置一种持久化存储方式，例如json文件存储方式。同时允许自定义存储方式（如sqlite、mysql等，不实现，但要定义）。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 自动持久化与会话恢复 (Priority: P1)

开发者使用本库构建 Agent 并启用了默认持久化后，Agent 在每次回复结束时自动将其完整状态保存到本地存储；当进程重启或应用重新部署时，开发者只需提供之前的会话标识，即可恢复出携带完整历史的 Agent——对话上下文、摘要、任务清单、权限与工具上下文全部还原，Agent 能基于完整历史继续作答，整个过程无需任何手动序列化或状态管理代码。

**Why this priority**: 这是本次需求的核心价值——让 agent 状态持久化成为框架开箱即用的内置能力，直接解决"进程退出即丢失会话"的根本痛点。没有自动落盘与恢复，其余能力都失去意义。

**Independent Test**: 用默认配置构建 Agent 并完成多轮对话，确认每次回复后状态已落盘；重启进程（或新进程）按同一会话标识重新构建 Agent，验证完整历史被恢复且 Agent 可基于历史继续作答。仅此一条故事即可构成可用 MVP。

**Acceptance Scenarios**:

1. **Given** 一个使用默认配置构建的 Agent，**When** 完成一轮回复，**Then** Agent 的完整状态被自动保存到本地存储，保存过程对开发者透明
2. **Given** 一个已产生多轮对话历史（含任务清单、摘要、上下文）的 Agent 会话，**When** 进程重启后按原会话标识重新构建 Agent，**Then** 对话上下文、摘要、任务清单、权限与工具上下文完整恢复，Agent 能基于完整历史正确作答
3. **Given** 一个正在回复的 Agent 会话，**When** 回复被中断或取消，**Then** 中断时刻的最新状态被保存，恢复会话后可从一致状态继续
4. **Given** 开发者提供一个不存在的会话标识，**When** 用于构建 Agent，**Then** 系统创建新会话而非报错崩溃，并可通过新的会话标识持久化

---

### User Story 2 - 自定义存储后端 (Priority: P2)

开发者已有自己的存储基础设施（如 SQLite、MySQL、Redis 或对象存储），希望 Agent 状态保存在其中而不是默认的 JSON 文件里。开发者通过实现库公开的存储后端接口接入自己的方案，即可让 Agent 的保存与恢复透明地走自有后端，行为与内置 JSON 文件后端完全一致，无需修改框架代码。

**Why this priority**: 持久化在真实部署中往往需要接入既有基础设施，可插拔的存储后端决定了该能力能否用于生产环境。它依赖 P1 提供完整的持久化契约才能安全落地，因此优先级次之。

**Independent Test**: 实现一个存储后端接口的最小自定义实现，用它构建 Agent 完成保存/恢复往返，验证与内置 JSON 文件后端行为一致；检查文档中是否给出以 SQLite/MySQL 为例的实现契约说明。

**Acceptance Scenarios**:

1. **Given** 一个实现了库公开存储接口的自定义后端（如基于 SQLite），**When** 用它构建 Agent 并完成保存/恢复，**Then** 行为与内置 JSON 文件后端一致，会话可保存、加载、列出与删除
2. **Given** 开发者使用自定义后端，**When** 加载一个不存在的会话，**Then** 返回明确的"未找到"结果，而不是崩溃或静默返回空数据
3. **Given** 文档中"实现自定义后端"部分，**When** 开发者查阅，**Then** 能获得存储接口的语义契约、以 SQLite/MySQL 为例的实现说明，无需反读框架源码

---

### User Story 3 - 会话管理 (Priority: P3)

开发者希望对自己持久化的会话进行管理：查看所有已保存的会话及其轻量元数据（创建时间、最后活跃时间、消息数、状态）、查询单个会话、删除不再需要的会话。这些操作不需要加载完整的会话状态即可完成，语义与 Python 参考实现的会话存储保持一致。

**Why this priority**: 会话管理是持久化能力的自然延伸，为运维与 UI 展示提供基础，但属于增量价值，P1/P2 落地后即可获得，因此优先级最低。

**Independent Test**: 对已持久化的多个会话执行列表、查询、删除操作，验证元数据正确且列表操作无需反序列化完整状态；删除不存在的会话不报错。

**Acceptance Scenarios**:

1. **Given** 多个已持久化的会话，**When** 开发者列出会话，**Then** 返回每个会话的标识与元数据（创建时间、最后活跃时间、消息数、状态），且列表示例在状态内容较大时依然快速返回
2. **Given** 一个已持久化的会话，**When** 开发者查询其元数据，**Then** 返回准确的结果
3. **Given** 一个已持久化的会话，**When** 开发者删除它，**Then** 会话被移除；再次删除同一会话不报错（幂等）

---

### Edge Cases

- 开发者提供的会话标识包含路径分隔符或非法字符时，存储实现不得产生目录穿越或意外覆盖其他文件的行为
- 会话文件损坏、被截断或内容不合法时，加载返回明确的结构化错误，且不导致进程崩溃或静默丢数据
- 会话文件为旧版本格式（缺少新增字段）时，按默认值兼容加载，不因字段缺失而失败
- 磁盘空间不足或无写权限时，保存返回明确的错误并向调用方报告，不破坏正在进行的推理循环
- 同一会话被并发触发多轮回复时，保存操作并发安全，不产生文件损坏或数据竞争
- 自动持久化被关闭时，Agent 运行全程不产生任何存储写入，行为与未引入持久化前一致
- 回复被中断或取消的瞬间，已产生的最新状态被保存，保证恢复点的一致性
- 会话在保存过程中进程崩溃，不得留下半个写入的损坏文件（保存须原子完成）
- 加载不存在的会话标识时，表现为创建新会话，而非报错
- 存储后端初始化失败（如目录不可创建）时，构建 Agent 给出明确错误，开发者可据此关闭持久化或改用其他后端

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供统一的会话存储后端接口，覆盖会话的保存（重复保存即更新，即 upsert 语义）、按标识加载、删除、列出会话标识、列出会话元数据等操作；接口语义必须与 Python 参考实现的会话存储保持一致
- **FR-002**: 系统必须内置一个 JSON 文件存储后端，作为默认持久化实现，不依赖任何外部服务即可将 agent 状态落盘；每个会话对应一个独立的 JSON 文件，文件内容包含会话元数据（标识、创建时间、最后活跃时间、消息数、状态）与完整的 agent 状态
- **FR-003**: 内置 JSON 文件后端必须支持跨进程重启后的状态恢复——按会话标识加载时，agent 状态的会话标识、摘要、对话上下文、回复上下文、权限上下文、工具上下文、任务上下文、中间件上下文等全部字段必须无损恢复
- **FR-004**: 内置 JSON 文件后端的状态写入必须原子完成，进程在写入中途崩溃不得留下损坏的会话文件；加载损坏或无法解析的会话文件必须返回明确的结构化错误，禁止静默失败或返回空状态
- **FR-005**: 构建 Agent 时必须支持注入存储后端与会话标识：未指定存储后端时使用默认的 JSON 文件后端；指定会话标识时从存储加载既有状态，未指定或不存在时创建新会话
- **FR-006**: Agent 在每次回复正常结束、以及回复被中断或取消时，必须将最新状态自动保存到已配置的存储后端；保存失败必须向调用方报告，且不得破坏正在进行的推理循环或 Agent 状态
- **FR-007**: 自动持久化必须可通过配置整体启用或禁用（默认启用）；禁用后 Agent 行为与未引入持久化时一致，运行全程不产生任何存储写入
- **FR-008**: 自定义存储后端（如 SQLite、MySQL、Redis 等）必须通过实现公开的存储后端接口接入，接口作为唯一的扩展点，开发者无需修改框架代码
- **FR-009**: 所有存储后端必须满足统一的会话语义：同一会话标识的重复保存即为更新；加载不存在的会话返回明确的"未找到"结果；删除不存在的会话幂等（不报错）
- **FR-010**: 会话元数据必须随保存自动更新，并支持独立于完整状态被列出——列出会话元数据不得要求反序列化每个会话的完整状态
- **FR-011**: 持久化的数据格式必须满足稳定数据协议：agent 状态的字段名与结构形状与 Python 参考实现保持一致；缺失字段按默认值处理，未知字段可忽略，新增字段不得破坏旧版本数据的加载
- **FR-012**: 存储相关的错误（文件读写、序列化、会话未找到、后端不可用等）必须类型明确、可追溯根因，并映射为稳定的机器可读错误类别，禁止依赖字符串内容判断错误类型
- **FR-013**: 存储后端的保存与加载操作必须并发安全，同一会话的并发读写不得产生数据竞争或文件损坏
- **FR-014**: 文档与示例必须演示：默认 JSON 文件存储的开箱即用方式、按会话标识恢复会话、以及实现自定义后端的语义契约说明（以 SQLite 与 MySQL 为例）

### Key Entities *(include if feature involves data)*

- **Session（会话）**: 一个 agent 会话的完整持久化单元，包含会话元数据（标识、创建时间、最后活跃时间、消息数、状态）与 agent 状态；是保存、加载、列表、删除操作的对象
- **Agent State（代理状态）**: 会话内的运行时状态，作为持久化的核心载荷，包含会话标识、摘要、对话上下文、回复上下文、权限上下文、工具上下文、任务上下文与中间件上下文；字段与 Python 参考实现保持一致
- **Storage Backend（存储后端）**: 会话持久化的统一扩展接口，定义保存、加载、删除、列出等操作语义；内置 JSON 文件实现与开发者自定义实现（SQLite、MySQL 等）均实现同一接口
- **Session Meta（会话元数据）**: 用于会话列表与概览的轻量信息（创建时间、最后活跃时间、消息数、状态），独立于完整 agent 状态维护与读取
- **会话存储文件**: 内置 JSON 文件后端中每个会话对应的一个 JSON 文件，记录会话元数据与完整 agent 状态

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 会话保存/加载往返后，agent 状态的全部字段（会话标识、摘要、对话上下文、回复/权限/工具/任务/中间件上下文）100% 无损恢复
- **SC-002**: 进程重启后按会话标识恢复的 Agent，可基于完整历史继续正确作答，端到端恢复成功率 100%（基于仓库内置集成测试场景）
- **SC-003**: 每次回复结束后（含正常结束与被中断/取消场景）最新状态自动落盘成功率为 100%
- **SC-004**: 接入自定义存储后端所需的框架改动为 0（仅需实现公开接口），接入后保存/加载/列表/删除行为与内置 JSON 文件后端一致
- **SC-005**: 损坏或格式非法的会话文件 100% 返回结构化错误，不产生进程崩溃或静默数据丢失
- **SC-006**: 持久化格式与 Python 参考实现的 agent 状态字段名与结构形状对齐度为 100%（除已记录差异外），旧版本数据文件 100% 可加载
- **SC-007**: 关闭自动持久化后，Agent 运行全程产生的存储写入次数为 0

## Assumptions

- Python 参考实现（AgentScope 2.0.5）的会话持久化后端为 Redis 与 SQL（SQLite/PostgreSQL/MySQL），需要外部服务，没有文件落盘实现；本特性内置的 JSON 文件后端是为 Rust 库提供"开箱即用"的本地持久化，二者共享相同的会话语义与 agent 状态数据形状
- 对话消息作为 agent 状态中对话上下文的一部分随会话整体持久化，不单独按消息建文件或建表（与 Python 应用层独立的消息存储不同，属库层简化，范围边界已明确）
- 自动持久化默认开启，可通过配置整体禁用；默认存储目录为工作目录下的 `sessions` 目录，可通过配置修改
- SQLite、MySQL 等自定义存储后端仅通过公开的存储后端接口定义其扩展点，本特性不提供这些后端的实现，也不将其加入内置配置项
- 本特性聚焦库内 agent 状态持久化，不包含 Python 参考实现中应用服务器层的分布式锁、消息总线、多用户/租户隔离等能力
- 兼容性分级为 L2 核心行为兼容与 L3 公开 API 语义兼容（会话存储语义对齐 Python 参考实现）；L1 字节级协议兼容不在本特性范围内
- 为接入持久化，构建 Agent 将新增可选配置（存储后端、会话标识、自动落盘开关），不删除或修改现有配置字段，保持既有调用方式向后兼容
