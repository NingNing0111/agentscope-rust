# Feature Specification: Session Management（会话管理）

**Feature Branch**: `010-session-management`

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "开始实现feature 010， session会话管理"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建和管理独立会话 (Priority: P1)

开发者需要为每个用户交互创建一个独立的会话实例。会话维护其自身的上下文消息历史、agent 状态和生命周期。开发者可以创建多个并行会话，每个会话之间相互隔离。

**Why this priority**: 这是 Session Management 最基本的价值——没有会话创建和管理，后续的持久化、修剪、恢复等功能都无从谈起。这是 MVP 的核心。

**Independent Test**: 可以通过创建两个独立会话、分别向它们输入不同的消息、验证它们的上下文互不干扰来独立测试。

**Acceptance Scenarios**:

1. **Given** 系统已初始化, **When** 开发者创建一个新会话并指定唯一标识符, **Then** 会话被成功创建，内部状态为空，会话 ID 与指定标识符一致
2. **Given** 一个新创建的会话, **When** 开发者在会话中执行一次 agent reply 操作, **Then** 会话内部上下文更新为新消息，其他会话不受影响
3. **Given** 两个并行运行的会话 A 和 B, **When** 在会话 A 中添加消息、在会话 B 中添加不同消息, **Then** 两个会话的上下文完全隔离，互不可见
4. **Given** 一个已有上下文的会话, **When** 开发者显式结束（close）该会话, **Then** 会话被标记为已关闭，与该会话关联的资源可被释放

---

### User Story 2 - 会话状态持久化与恢复 (Priority: P2)

开发者可以将会话的完整状态（包括消息上下文、agent 状态、reply 上下文、中间件上下文等）持久化到存储中，并在之后从存储中恢复，继续之前的对话。

**Why this priority**: 持久化是多轮对话应用的关键需求——用户关闭浏览器后回来继续对话、服务重启后恢复会话状态都需要此能力。

**Independent Test**: 可以通过创建一个会话、添加一些消息、持久化它、然后从持久化数据恢复一个新会话并验证上下文完全一致来独立测试。

**Acceptance Scenarios**:

1. **Given** 一个包含 5 条消息的活跃会话, **When** 开发者调用 save 操作, **Then** 会话完整状态（包括所有消息、reply 上下文、middle_context）被序列化并写入存储
2. **Given** 存储中存在一个已保存的会话数据, **When** 开发者调用 load 操作并指定会话 ID, **Then** 会话被完全恢复，包括此前所有消息历史、reply 上下文和工具缓存状态
3. **Given** 一个已保存的会话, **When** 开发者从存储中删除该会话, **Then** 会话数据从存储中移除，后续无法再加载该会话
4. **Given** 一个已被恢复的会话, **When** 开发者继续执行 reply 操作, **Then** 新消息在原有上下文基础上追加，延续被保存前的对话状态

---

### User Story 3 - 会话上下文修剪与压缩 (Priority: P3)

当一个会话的消息上下文增长到接近模型的上下文窗口限制时，系统能够自动或手动修剪/压缩早期的消息，确保会话可以持续运行而不超出模型限制。

**Why this priority**: 在长对话中，上下文窗口溢出会导致模型调用失败。修剪是解决此问题的关键机制，但它需要在基本会话和持久化能力建立后才能有效运作。

**Independent Test**: 可以通过创建一个包含大量消息（接近阈值）的会话、验证修剪后上下文消息数量降至阈值以下、且最近的 N 条关键消息被保留来独立测试。

**Acceptance Scenarios**:

1. **Given** 一个会话配置了最大消息数限制为 10, **When** 会话中的消息数达到 10 条并试图追加第 11 条, **Then** 系统根据修剪策略移除早期消息，使消息数保持在限制内
2. **Given** 一个启用了自动压缩的会话, **When** 上下文 token 数量接近窗口限制, **Then** 早期消息被摘要压缩，以压缩后的摘要形式保留
3. **Given** 一个被修剪的会话, **When** 修剪操作执行, **Then** 最近的 N 条消息及其关联的工具调用响应链完整保留，不被裁断
4. **Given** 一个会话的历史消息, **When** 开发者查看修剪后的上下文, **Then** 关键的结构化信息（如系统提示、用户原始问题）以某种形式被保留

---

### User Story 4 - 会话级别的中间件上下文 (Priority: P3)

中间件（Middleware）可以在会话级别存储和管理自己的状态数据。每个会话为每个中间件提供独立的上下文存储空间，中间件之间互不干扰。

**Why this priority**: 中间件上下文已经在 `AgentState.middle_context` 中有基础实现。Feature 010 需要将其正式化为会话管理的一部分，确保中间件在会话的完整生命周期（创建→持久化→恢复→关闭）中都能正确访问和更新自己的状态。

**Independent Test**: 可以通过注册一个中间件到会话、在中间件执行期间写入会话上下文、然后验证另一个中间件或后续执行中能读取到该上下文来独立测试。

**Acceptance Scenarios**:

1. **Given** 一个会话注册了 MemoryMiddleware, **When** MemoryMiddleware 在 pre_reply 阶段写入 memory 查询结果, **Then** 该结果被存储在会话的 middle_context 中，仅对该会话可见
2. **Given** 一个会话已持久化并包含 middle_context 数据, **When** 从存储中恢复该会话, **Then** 所有中间件的上下文数据被完整恢复
3. **Given** 两个独立的会话 A 和 B, **When** 在会话 A 的中间件中写入数据, **Then** 会话 B 的中间件看不到会话 A 的数据

---

### Edge Cases

- 会话关闭后，尝试对其执行操作（如 reply、append_context）应返回明确的 SessionClosed 错误
- 会话 ID 冲突：尝试创建已存在的会话 ID 时应返回错误，或由调用方显式选择覆盖行为
- 持久化存储不可用时（网络中断、磁盘满），save/load 操作应返回明确的错误而非静默失败
- 并发访问同一会话：多个并发操作同时修改一个会话的状态时，需要定义冲突解决策略
- 超大上下文修剪：当修剪阈值极小（如 max=1）时，系统应能正确处理而不 panic
- 空会话持久化：一个没有任何消息的空会话也应能被正常持久化和恢复
- 会话恢复时的版本兼容：从旧版本格式的持久化数据恢复时，应能正确处理（或返回明确的版本不兼容错误）
- 嵌套 reply 保护：在会话的一次 reply 未完成时，不应允许同一会话启动新的 reply

## Requirements *(mandatory)*

### Functional Requirements

**会话生命周期**:

- **FR-001**: 系统 MUST 提供创建会话的能力，每个会话具有唯一标识符
- **FR-002**: 系统 MUST 支持查询会话的当前状态（活跃、已关闭、已暂停等）
- **FR-003**: 系统 MUST 支持显式关闭会话，关闭后该会话不接受新的操作请求
- **FR-004**: 系统 MUST 在会话关闭时确保关联的异步任务在可配置的超时时间内终止
- **FR-005**: 系统 MUST 支持多个会话并行运行且状态完全隔离

**消息上下文管理**:

- **FR-006**: 系统 MUST 维护每个会话的消息历史（context），支持追加新消息
- **FR-007**: 系统 MUST 支持配置每个会话的最大消息数量限制
- **FR-008**: 系统 MUST 在消息数达到限制时拒绝追加并返回明确的错误（而非静默丢弃）

**会话持久化**:

- **FR-009**: 系统 MUST 提供将会话完整状态序列化为可存储格式的能力
- **FR-010**: 系统 MUST 支持从序列化数据恢复（反序列化）会话的完整状态
- **FR-011**: 系统 MUST 支持删除已持久化的会话数据
- **FR-012**: 系统 MUST 在序列化/反序列化失败时返回明确的错误（包含失败原因）

**上下文修剪**:

- **FR-013**: 系统 MUST 提供根据消息数量阈值修剪会话上下文的机制
- **FR-014**: 修剪操作 MUST 保留最近的 N 条消息，以及与其关联的工具调用和工具结果
- **FR-015**: 系统 MUST 支持可配置的修剪策略（保留最近 N 条、保留系统提示等）
- **FR-016**: 修剪后的会话 MUST 保持内部状态一致性（如 reply_id 引用仍然有效）

**中间件上下文**:

- **FR-017**: 系统 MUST 为每个会话提供中间件可读写的数据存储区域（middle_context）
- **FR-018**: 中间件上下文 MUST 与消息历史一同参与会话的持久化和恢复
- **FR-019**: 中间件上下文 MUST 在会话之间完全隔离

**状态与追踪**:

- **FR-020**: 系统 MUST 为会话状态变化（创建、关闭、修剪、持久化、恢复）发出对应的事件
- **FR-021**: 系统 MUST 在会话相关的操作中携带 session_id 用于追踪和调试
- **FR-022**: 系统 MUST 支持通过 session_id 查询会话的元信息（创建时间、消息数量、状态等）

### Key Entities

- **Session**: 代表一个对话会话。核心属性：ID（唯一标识符）、状态（活跃/已关闭）、消息上下文（消息历史列表）、AgentState（agent 运行时状态，包含 session_id、reply 上下文、middle_context 等）、元信息（创建时间、最后活跃时间）。生命周期：Create → Active → Closed。

- **SessionStore**: 会话持久化存储的抽象。提供 save（保存）、load（加载）、delete（删除）、list（列举）操作。不假定具体存储后端（内存、文件、数据库等均可）。

- **TrimStrategy**: 上下文修剪策略配置。定义修剪触发条件（消息数阈值、token 数阈值）和保留规则（保留最近 N 条、保留系统提示、保留工具调用链完整性）。

- **SessionMeta**: 会话元信息。包含创建时间、最后活跃时间、消息数量、状态等轻量级信息，用于会话列表展示和快速查询，无需加载完整会话数据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 开发者可以在 5 行代码内创建一个会话并执行一次基本的 reply 操作
- **SC-002**: 系统支持同时维护至少 100 个活跃会话，且会话之间的上下文完全隔离（零交叉污染）
- **SC-003**: 会话持久化与恢复的往返操作（save → load → verify）在包含 100 条消息的会话上耗时不超过 100 毫秒
- **SC-004**: 上下文修剪后，关键工具调用链（tool call → tool result 对）100% 保持完整，不出现孤立的 tool call 或 tool result
- **SC-005**: 会话关闭后，与该会话关联的后台异步任务在 5 秒内全部停止
- **SC-006**: 100% 的会话状态变化（创建、关闭、修剪、持久化、恢复）都有对应的可观测事件发出

## Assumptions

- Session 持久化的存储后端通过 trait 抽象定义，默认提供内存实现用于测试，具体存储实现（如文件系统、Redis）属于后续 feature 或 provider crate 的职责
- 上下文修剪中的 token 计数依赖于 Model trait 提供的 token 计数能力（已由 Feature 003 定义）
- middle_context 的数据结构沿用现有 `HashMap<String, serde_json::Value>` 格式，与 Feature 009 Memory System 兼容
- 会话的并发访问保护（如 Mutex/RwLock）在实现层面处理，不在此 spec 中定义具体并发原语
- 会话的序列化格式与 AgentState 现有格式兼容，优先使用 serde_json（与现有架构一致）
- 上下文压缩（将消息摘要为简短文本）依赖 Feature 007 中已有的 `context_compression` 模块
- Python AgentScope 参考实现中的 Session 行为作为兼容性基准——session_id 的格式、session 状态变化的语义等需与之保持一致
- 本 feature 专注于单个进程内的 Session 管理，分布式 Session（跨进程/跨节点）不在当前范围内
