# 文档页面契约（Doc Page Contract）

**目的**: 定义 `docs/rust/zh/` 下每个 `.mdx` 页面必须满足的结构与内容约束，保证 50 个页面格式统一、状态标注一致、可被工具校验。

## 1. 文件与格式

- 每个页面是一个 `.mdx` 文件，路径与 `docs/python/zh` 严格一一对应（见 mirror-map）。
- 顶部为 YAML frontmatter，含 `title`（字符串）与 `description`（一句话）。
- 正文使用 Markdown + Mintlify 组件，与 docs/python 同款语法。

## 2. 状态标注（Status Annotation）

每个页面在其正文顶部（frontmatter 之后、首节之前）MUST 放置一个统一的状态块，声明该能力在 Rust 中的实现状态。状态块使用 `<Note>` 组件，格式如下：

```mdx
<Note>
**Rust 实现状态**: 已实现（参考 Python 文档页：`<docs/python 相对路径>`）
</Note>
```

三种状态及文案模板：

| 状态 | 文案 | 适用 |
|------|------|------|
| 已实现 | `Rust 实现状态: 已实现。本文档描述的能力在 AgentScope Rust 中可用，兼容基线为 AgentScope Python v2.0.5。` | 能力已实现且文档内容为真实 Rust 用法 |
| 部分支持 | `Rust 实现状态: 部分支持。已支持 <列出支持范围>；以下能力在 Rust 中尚未实现：<列出缺失>。` | 能力在 Rust 中仅部分可用，须给出边界 |
| 计划中 | `Rust 实现状态: 计划中。该能力在 AgentScope Python <版本> 中提供，AgentScope Rust 尚未实现，预计在后续版本推出。` | 能力在 Rust 中未实现 |

**规则**：
- 三档为唯一合法取值，禁止其他措辞（禁止「兼容」「完全支持」等模糊表述）。
- 「部分支持」MUST 至少列出「已支持」与「尚未实现」两列。
- 状态块必须与兼容性矩阵/镜像映射清单的记录一致。
- 计划中页面 MUST NOT 出现 Rust 代码示例或伪造的 Rust API 用法；可描述 Python 侧能力简介与 Rust 缺失范围，可指向替代能力页面。

## 3. 结构约定

- 已实现页面的章节结构遵循 docs/python 对应页面的章节骨架，但内容替换为 Rust 真实用法。
- 页面中的代码块：MUST 只引用 `examples/` 下示例的**真实运行输出**或**示例源码的摘录**，禁止粘贴无法编译的虚构代码。推荐以「运行 `cargo run -p <example> -- ...`」+ 预期输出展示。
- 站内链接使用版本化路径 `/versions/<rust-ver>/zh/<path>`，`<rust-ver>` 与 `Cargo.toml` 的 `version` 一致（当前 `0.1.0`）。
- 每个已实现页面 MUST 至少包含一个「运行示例」小节，给出示例路径、运行命令与预期行为；无凭据运行时的错误行为也要说明。

## 4. 兼容性等级标注

已实现页面 MUST 在适当位置（如概述或末尾）标注该模块的兼容性等级（L1-L4，定义见宪法 §18），格式：

```mdx
| 模块 | 兼容等级 | 说明 |
|------|----------|------|
| <模块> | L<n> | <一句话，与兼容性矩阵一致> |
```

## 5. 可校验性

- 文档中所有 `cargo run -p <name>` 与示例路径 MUST 与 `examples/` 下的实际 crate 一一对应（脚本校验）。
- 所有站内链接 MUST 指向存在的目标页面（脚本校验悬空链接）。
- frontmatter 的 `title`/`description` 必填；状态块 MUST 存在于每个页面（脚本校验）。

## 6. 反模式（禁止）

- ❌ 未实现能力页面出现 Rust 代码或伪 API（违宪 §5）。
- ❌ 「即将支持」「差不多支持」等模糊状态措辞。
- ❌ 粘贴无法编译的代码片段替代 examples/ 引用。
- ❌ 在计划中页面声称某项能力可用。
