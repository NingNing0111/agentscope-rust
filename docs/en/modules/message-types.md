# Message & Basic Types

> One-liner: the unified data protocol behind all AgentScope communication — the `Msg` message structure and the `ContentBlock` system, forming the data-exchange foundation for every module (Agent, model, memory, session, RAG).

## 1. Overview

This module covers two foundation crates at the bottom of the layered architecture, depending on no other AgentScope crate:

| Crate | Responsibility |
|-------|----------------|
| `agent_scope_message` | The `Msg` message structure, the `ContentBlock` system, data sources, tool-call state machines, message factory functions |
| `agent_scope_types` | Cross-crate shared types: error classification (`ErrorType`/`ErrorInfo`), reply finished reason (`ReplyFinishedReason`), hook type markers, JSON type aliases |

**When to use**: any scenario that constructs, reads, filters, or serializes messages — sending user input to an Agent, parsing model replies, persisting session records, inspecting message content in custom middleware.

**Prerequisites**: none (this module is the prerequisite for all other module docs).

## 2. Core Concepts & Main Public Types

### 2.1 The `Msg` Structure

`Msg` is the core message type in AgentScope, composed of a sender name, a role, and a list of content blocks:

| Field | Type | Description |
|-------|------|-------------|
| `name` | `String` | Sender / agent name |
| `content` | `Vec<ContentBlock>` | Content blocks composing the message body |
| `role` | `Role` | Role discriminator: `User` / `Assistant` / `System` (serialized lowercase) |
| `id` | `String` | Unique identifier; auto-generated UUID when absent at construction or deserialization |
| `metadata` | `serde_json::Value` | Arbitrary metadata dictionary; defaults to an empty object |
| `created_at` | `String` | RFC 3339 creation timestamp; auto-generated by default |
| `usage` | `Option<Usage>` | Token usage (`input_tokens`/`output_tokens`); written after the model call completes |
| `finished_at` | `Option<String>` | When the message was finalized |
| `finished_reason` | `Option<ReplyFinishedReason>` | Why the reply finished: `completed`/`interrupted`/`exceed_max_iters`/`error` |
| `structured_output` | `Option<serde_json::Value>` | Structured output (e.g., JSON mode / function calling results) |
| `error` | `Option<ErrorInfo>` | Structured error info when the message represents a failure |

All `Option` fields are omitted from serialized output when `None` (`skip_serializing_if`).

### 2.2 `ContentBlock`

`ContentBlock` is an enum discriminated by a `type` tag (serde tagged union) with 6 block types:

| Variant (`type` tag) | Payload type | Responsibility |
|---------------------|--------------|----------------|
| `"text"` | `TextBlock { text, id, created_at, finished_at }` | Plain text |
| `"thinking"` | `ThinkingBlock { thinking, ..., extras }` | Model reasoning content; `extras` passes provider-private fields through via `#[serde(flatten)]` (e.g., signatures) |
| `"hint"` | `HintBlock { hint: HintContent, source, ... }` | One-shot, non-streaming hint/instruction content; `HintContent` is a string or a block list (untagged) |
| `"data"` | `DataBlock { source: DataSource, name, ... }` | Binary data; `DataSource` is `"base64"` (`Base64Source{data, media_type}`) or `"url"` (`URLSource{url, media_type}`) |
| `"tool_call"` | `ToolCallBlock { id, name, input, state, suggested_rules, ... }` | Tool call request; `input` is a **raw, unparsed JSON string** (the Foundation layer does not parse arguments) |
| `"tool_result"` | `ToolResultBlock { id, name, output, state, metadata, is_last, ... }` | Tool execution result; `output` is a string or block list (untagged `ToolOutput`); `is_last` marks the final chunk of a streaming tool result |

At runtime, use `block_type()` to get the `BlockType` discriminator (`Text`/`Thinking`/`Hint`/`Data`/`ToolCall`/`ToolResult`).

### 2.3 Roles & Validation Rules

`Msg::new(name, content, role)` validates role-content compatibility at construction; violations return `ValidationError::InvalidContentForRole`:

| Role | Allowed block types |
|------|---------------------|
| `Role::User` | `Text`, `Data` only |
| `Role::System` | `Text` only |
| `Role::Assistant` | All block types (unrestricted) |

### 2.4 Tool Call State Machines

Two state enums serialize alongside their blocks (lowercase values):

- `ToolCallState`: `pending` (default) → `asking` → `allowed` → `submitted` → `finished`
- `ToolResultState`: `running` (default) → `success` / `error` / `interrupted` / `denied`

`PermissionRule` is currently a placeholder struct (`extras` transparently passes arbitrary fields through) and will be completed by the permission module.

### 2.5 Serialization Protocol

User-observable serialization semantics (Constitution Article XII: stable data protocol):

1. **Type tags**: both `ContentBlock` and `DataSource` are discriminated by a `type` field; block tags are `text`/`thinking`/`hint`/`data`/`tool_call`/`tool_result`.
2. **Forward compatibility**: deserialization never fails on unknown block types — they are absorbed into the `ContentBlock::Unknown` placeholder variant, whose `block_type()` falls back to `Text` on a best-effort basis. Note: this variant does not retain the original fields, so re-serialization loses the original content (lossy).
3. **Auto-completion of defaults**: missing `id` generates a UUID; missing `created_at` generates an RFC 3339 timestamp; `metadata` defaults to an empty object.
4. **Optional field omission**: `usage`/`finished_at`/`finished_reason`/`structured_output`/`error` do not appear in JSON when `None`.
5. **Enum value styles**: `Role` and the state machines are lowercase (`"user"`/`"pending"`); `ErrorType` and `ReplyFinishedReason` are snake_case (`"rate_limit"`/`"exceed_max_iters"`).

### 2.6 Shared Error Types (`agent_scope_types`)

| Type | Description |
|------|-------------|
| `ErrorType` | Fatal error classification: `authentication`/`permission`/`rate_limit`/`invalid_request`/`upstream`/`connection`/`internal`/`unknown` |
| `ErrorInfo { error_type, message }` | Structured, UI-facing error description; `error_type` serializes as field `"type"` and defaults to `unknown` |
| `ReplyFinishedReason` | `completed`/`interrupted`/`exceed_max_iters`/`error` |

## 4. Usage Patterns

### 4.1 Creating Messages with Factory Functions

`agent_scope_message` provides factory functions for all three roles, handling validation and timestamps automatically:

```rust
use agent_scope_message::{user_msg, system_msg, assistant_msg};

// user / system factories return Result (blocks may violate role validation)
let user = user_msg("user", "Hello")?;
let sys = system_msg("system", "You are a helpful assistant")?;

// assistant factory does not return Result (Assistant accepts all block types)
// and finished_at stays None — assistant messages are built incrementally
let asst = assistant_msg("assistant", "Hi there!");
```

Behavioral difference (source: `crates/agent_scope_message/src/factory.rs`): `user_msg`/`system_msg` set `finished_at` to `created_at` (complete upon creation); `assistant_msg` leaves `finished_at` as `None` (built incrementally, finalized later).

### 4.2 Filtering and Checking Content Blocks by Type

```rust
use agent_scope_message::BlockType;

// Some(block_type) returns only that type; None returns all
let texts = msg.get_content_blocks(Some(BlockType::Text));
let has_tool_call = msg.has_content_blocks(Some(BlockType::ToolCall));
let is_empty = !msg.has_content_blocks(None);
```

### 4.3 Extracting Plain Text Content

`get_text_content(separator)` concatenates the text of all `TextBlock`s, returning `None` when there are none:

```rust
if let Some(text) = msg.get_text_content("\n") {
    println!("{text}");
}
```

### 4.4 Handling Unknown Block Types (Forward Compatibility)

When deserializing messages produced by third parties or newer protocol versions, unknown block types do not cause parse failures:

```rust
// JSON containing "type": "image" (unknown in this version) still deserializes into Msg
// Unknown blocks become ContentBlock::Unknown; iteration falls back via block_type() == BlockType::Text
for block in msg.get_content_blocks(None) {
    match block {
        ContentBlock::Text(t) => { /* ... */ }
        ContentBlock::ToolCall(tc) => { /* ... */ }
        _ => { /* Unknown and other variants */ }
    }
}
```

Note: the `Unknown` variant does not retain original fields — use `serde_json::Value` directly when you need lossless handling of unknown protocols.

## 5. Errors & Unsupported Capabilities

| Error type | Trigger condition |
|------------|-------------------|
| `ValidationError::InvalidContentForRole { role, disallowed_types }` | `Msg::new` (and the `user_msg`/`system_msg` factories) receive blocks violating role validation |
| `ValidationError::EmptyContent` | Message content is empty (optional check, not enforced on current construction paths) |
| `AppendEventError::ReplyIdMismatch` | Event `reply_id` does not match the message `id` (when applying event streams to a message) |
| `AppendEventError::BlockNotFound` | The content block referenced by an event does not exist |
| `AppendEventError::UnknownEventType` | Unrecognized event type |

**Unsupported capabilities**: none. This module is a pure data protocol with no `UnsupportedFeature` paths.

**FAQ**:

- *Data "disappears" after deserializing messages with unknown blocks*: unknown blocks are absorbed as `ContentBlock::Unknown` without retaining original fields (see 4.4).
- *Why can't `assistant_msg` fail?*: the Assistant role accepts all block types, so validation always passes and the factory uses `expect` internally.

## 6. Compatibility

- **Compatibility level**: **L1** (field-by-field data structure compatibility; message factory functions and role specialization at **L2** — behaviorally equivalent with Rust-idiomatic signatures)
- **Authoritative source**: `specs/001-compatibility-baseline/capability-matrix.json`
- **Known deviations**:
  - The matrix `status` field is currently `NOT_ANALYZED` for all entries (the matrix has not been backfilled after Features 001-017; backfill is tracked as follow-up work). Levels on this page are cross-verified against matrix `target_level` (LL1/LL2 for `message-*`/`types-*` entries) + `specs/002-foundation-layer` + actual code state.
  - The `ContentBlock::Unknown` forward-compatibility placeholder is a Rust-side enhancement — Python handles unknown block types differently; Rust absorbs unknown blocks but re-serialization is lossy (original fields are not preserved).
  - `assistant_msg`/`assistant_msg_with_blocks` do not return `Result` (internal `expect`) — asymmetric with `user_msg`/`system_msg` signatures, a Rust-idiomatic difference.
  - `ToolCallBlock.input` is a raw, unparsed JSON string (the Foundation layer does not parse tool arguments) — argument parsing happens at the Tool layer.
- **Unsupported capabilities**: none.
