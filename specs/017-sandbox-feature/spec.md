# Feature Specification: Sandbox Feature（代码执行沙箱）

**Feature Branch**: `017-sandbox-feature`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "实现sandbox feature"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在受控沙箱中执行命令 (Priority: P1) 🎯 MVP

作为开发者，我希望 Agent 在一个受控、隔离的执行环境中运行命令和读写临时文件，而不是直接暴露宿主机工作目录，使 Agent 可以完成代码执行、脚本验证和文件处理任务，同时降低误操作影响宿主环境的风险。

**Why this priority**: 沙箱的核心价值是安全执行。没有受控执行环境，后续 Workspace、Tool、Agent 只能依赖本地后端，无法为不可信或半可信任务提供隔离边界。

**Independent Test**: 创建一个沙箱会话，执行简单命令并写入文件，验证命令输出可获取、文件只存在于沙箱可见目录内、退出后资源可清理。

**Acceptance Scenarios**:

1. **Given** 一个新建的沙箱会话, **When** 用户执行一条返回文本的命令, **Then** 系统返回退出码、标准输出、标准错误和执行耗时
2. **Given** 一个沙箱会话绑定了工作目录, **When** 用户在沙箱内创建文件, **Then** 文件可通过该沙箱读取，但不会写入未授权的宿主机路径
3. **Given** 命令超过配置的执行时限, **When** 沙箱终止该命令, **Then** 系统返回明确的超时错误并保留可诊断的执行信息
4. **Given** 沙箱会话已关闭, **When** 用户再次请求执行命令, **Then** 系统拒绝请求并返回明确的生命周期错误

---

### User Story 2 - 将 Workspace 绑定到沙箱后端 (Priority: P2)

作为开发者，我希望现有 Workspace 能够选择沙箱作为执行后端，使 Bash、Read、Write、Edit、Grep 等工作空间工具都在同一个沙箱边界内运行，从而让 Agent 的文件和进程操作保持一致的隔离语义。

**Why this priority**: Feature 012 已提供 Workspace 抽象；沙箱只有接入 Workspace 后，才能被 Agent 和 Tool 系统自然使用，形成端到端价值。

**Independent Test**: 创建一个使用沙箱后端的 Workspace，调用工作空间工具执行文件写入、读取和命令运行，验证所有操作都发生在沙箱工作目录内。

**Acceptance Scenarios**:

1. **Given** 一个配置为沙箱后端的 Workspace, **When** 用户调用文件写入工具, **Then** 文件写入沙箱工作目录并可通过同一 Workspace 读取
2. **Given** 一个配置为沙箱后端的 Workspace, **When** 用户调用命令执行工具, **Then** 命令在沙箱环境中运行并返回标准化执行结果
3. **Given** 用户尝试通过相对路径或符号链接访问工作目录外部资源, **When** 操作被提交给 Workspace, **Then** 系统拒绝该访问并返回路径越界错误
4. **Given** Workspace 被 reset 或 close, **When** 其沙箱后端仍有临时资源, **Then** 资源被清理或进入可审计的已关闭状态

---

### User Story 3 - 限制资源与网络访问 (Priority: P3)

作为平台开发者，我希望为沙箱配置 CPU、内存、执行时限、文件系统写入范围和网络策略，使不同信任等级的 Agent 任务可以使用不同隔离强度，避免失控命令消耗过多资源或访问不应访问的外部网络。

**Why this priority**: 资源限制和网络策略是从“可运行”走向“可安全托管”的关键能力，但依赖 US1 的基本执行能力和 US2 的 Workspace 集成。

**Independent Test**: 创建带有限制策略的沙箱，分别执行超时命令、大输出命令、越界文件访问和网络访问，验证策略按配置生效并产生可理解错误。

**Acceptance Scenarios**:

1. **Given** 沙箱配置了最大执行时限, **When** 命令运行超过时限, **Then** 命令被终止并返回超时状态
2. **Given** 沙箱配置了最大输出大小, **When** 命令产生超大输出, **Then** 系统截断或分段保存输出，并明确告知用户输出未完整内联返回
3. **Given** 沙箱配置为禁用网络, **When** 命令尝试访问外部网络, **Then** 请求失败且不会绕过沙箱策略
4. **Given** 沙箱配置了只读挂载, **When** 命令尝试修改该区域文件, **Then** 写入被拒绝并返回权限错误

---

### User Story 4 - 记录可审计的沙箱执行历史 (Priority: P4)

作为调试者或平台维护者，我希望查看每个沙箱会话的执行历史，包括命令、时间、退出状态、资源限制命中情况和输出引用，以便复现问题、定位失败原因并生成兼容性报告。

**Why this priority**: 审计记录不是 MVP 的运行前提，但对安全隔离、错误诊断和宪法要求的兼容性报告至关重要。

**Independent Test**: 在沙箱会话中执行多条命令，随后查询执行历史，验证记录顺序、状态、输出摘要和错误原因完整可读。

**Acceptance Scenarios**:

1. **Given** 一个沙箱会话执行了多条命令, **When** 用户查询执行历史, **Then** 系统按时间顺序返回每次执行的命令摘要、状态和耗时
2. **Given** 某次命令因超时、权限或路径越界失败, **When** 用户查看执行记录, **Then** 记录包含明确失败类别和用户可理解说明
3. **Given** 某次命令输出较大, **When** 用户查看执行历史, **Then** 系统展示输出摘要并提供沙箱内的完整输出引用

---

### Edge Cases

- 沙箱运行环境不可用时，创建会话应返回稳定错误，不得静默退回到非隔离本地执行
- 沙箱初始化过程中失败时，已创建的临时目录和部分资源应被清理
- 命令返回非零退出码时，应作为正常执行结果返回，而不是被误判为系统故障
- 命令产生大量输出时，应防止内存无限增长，并保留可追踪的输出位置
- 用户传入空命令、非法路径、无效资源限制或不存在的挂载源时，应返回可理解的参数错误
- 沙箱关闭时仍有命令运行，应终止或等待至配置的宽限期后清理
- 多个沙箱会话并发运行时，会话之间的文件、环境变量和执行历史不得互相泄漏
- 不支持的沙箱能力必须返回明确的 UnsupportedFeature 或等价稳定错误，不得伪装成功
- 当宿主平台缺少必要隔离能力时，应明确报告兼容性等级和降级原因
- 路径规范化必须处理 `..`、重复分隔符和符号链接，防止逃逸工作目录

## Requirements *(mandatory)*

### Functional Requirements

#### 沙箱会话生命周期

- **FR-001**: 系统 MUST 允许用户创建独立的沙箱会话，每个会话拥有唯一标识、独立工作目录、环境配置和生命周期状态
- **FR-002**: 系统 MUST 支持显式初始化、关闭和清理沙箱会话，并保证这些操作可重复调用且结果稳定
- **FR-003**: 系统 MUST 在沙箱会话关闭后拒绝新的文件或命令操作，并返回明确的生命周期错误
- **FR-004**: 系统 MUST 在初始化失败或异常关闭时清理已创建但未交付给用户的临时资源

#### 命令执行

- **FR-005**: 系统 MUST 支持在沙箱会话中执行命令，并返回退出码、标准输出、标准错误、开始时间、结束状态和耗时
- **FR-006**: 系统 MUST 区分命令自身失败与沙箱系统故障；非零退出码 MUST 作为可观察执行结果返回
- **FR-007**: 系统 MUST 支持为单次命令设置执行时限，超时后终止命令并返回明确的超时状态
- **FR-008**: 系统 MUST 限制单次命令可内联返回的输出大小，超过限制时保留摘要和完整输出引用
- **FR-009**: 系统 MUST 支持为命令配置环境变量和工作目录，但工作目录必须限制在沙箱授权范围内

#### 文件系统隔离

- **FR-010**: 系统 MUST 将沙箱内文件读写限制在授权工作目录或显式挂载范围内
- **FR-011**: 系统 MUST 防止通过路径遍历、符号链接或路径别名访问沙箱授权范围外的宿主资源
- **FR-012**: 系统 MUST 支持只读和可写两类挂载语义，并在写入只读区域时返回权限错误
- **FR-013**: 系统 MUST 为沙箱会话提供临时目录，并在会话清理后删除临时文件，除非用户显式选择保留

#### Workspace 与 Tool 集成

- **FR-014**: 系统 MUST 允许 Workspace 选择沙箱作为执行后端，使文件工具和命令工具共享同一沙箱边界
- **FR-015**: 系统 MUST 保持 Workspace 工具的外部行为一致：同样的读、写、搜索和命令请求在沙箱后端下返回等价结构化结果
- **FR-016**: 系统 MUST 在 Workspace reset 或 close 时同步处理关联沙箱会话，避免孤儿执行环境
- **FR-017**: 系统 MUST 提供用户可理解的沙箱工作区说明，告知 Agent 文件应写入的位置、哪些路径可用以及哪些操作会被拒绝

#### 策略与安全控制

- **FR-018**: 系统 MUST 支持配置执行时限、输出大小限制、可写路径范围和网络访问策略
- **FR-019**: 系统 SHOULD 支持配置 CPU、内存或进程数量限制；当宿主环境无法支持时，MUST 返回明确的 UnsupportedFeature 或能力不可用错误
- **FR-020**: 系统 MUST 禁止静默降级到非隔离执行；任何隔离能力不可用都必须显式暴露给调用方
- **FR-021**: 系统 MUST 对不安全或未授权操作返回稳定错误类别，便于上层 Agent、Tool 和测试断言

#### 审计与兼容性

- **FR-022**: 系统 MUST 记录每个沙箱会话的执行历史，包括命令摘要、状态、耗时、失败类别和输出引用
- **FR-023**: 系统 MUST 能够生成沙箱能力摘要，说明当前环境支持的隔离能力、限制能力和不支持能力
- **FR-024**: 系统 MUST 在兼容性矩阵中登记 Sandbox 模块的目标兼容等级和已知偏差
- **FR-025**: 系统 MUST 覆盖与 Python AgentScope sandbox/workspace 相关能力的可观察行为差异，无法兼容的部分必须登记为 UnsupportedFeature

### Key Entities *(include if feature involves data)*

- **Sandbox Session（沙箱会话）**: 一个隔离执行环境的生命周期实例，包含唯一标识、工作目录、状态、策略、挂载信息和执行历史。它是命令执行和文件隔离的基本边界。

- **Sandbox Policy（沙箱策略）**: 描述资源与安全限制的配置集合，包括执行时限、输出大小、网络策略、可写路径范围、只读挂载和可选资源限制。

- **Sandbox Mount（沙箱挂载）**: 将宿主或临时资源暴露给沙箱的授权路径映射，包含沙箱内路径、访问模式、是否持久化和生命周期归属。

- **Execution Result（执行结果）**: 单次命令运行的可观察结果，包含命令摘要、退出码、标准输出摘要、标准错误摘要、完整输出引用、开始/结束时间、耗时和状态类别。

- **Sandbox Workspace Backend（沙箱工作空间后端）**: Workspace 使用的沙箱执行适配层，使工作空间工具通过沙箱会话完成文件和命令操作，并继承同一隔离策略。

- **Capability Report（能力报告）**: 当前运行环境对沙箱能力的支持声明，包括可用能力、不支持能力、兼容性等级和已登记偏差。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 开发者可以在 10 行以内创建一个沙箱会话、执行一条命令并获得结构化执行结果
- **SC-002**: 100% 的沙箱命令执行结果都能明确区分成功、非零退出、超时、权限拒绝和沙箱系统错误
- **SC-003**: 路径越界、符号链接逃逸和只读挂载写入三类安全场景均被测试覆盖并稳定拒绝
- **SC-004**: Workspace 使用沙箱后端时，文件读写和命令执行的主要用户流程与本地 Workspace 保持等价结果结构
- **SC-005**: 沙箱会话关闭或 reset 后，不遗留可由后续测试观察到的临时文件、运行中命令或活跃会话状态
- **SC-006**: 不支持的沙箱能力 100% 返回明确错误，并在能力报告或兼容性矩阵中可追踪
- **SC-007**: 对 20 个并发沙箱会话执行基础命令和文件操作时，会话之间无文件内容、环境变量或执行历史泄漏
- **SC-008**: Sandbox 模块达到至少 L2（核心行为兼容）目标；若无法达到 L3/L4，所有差异均有兼容性记录

## Assumptions

- 本 Feature 聚焦代码执行沙箱，不包含 Multi-agent 协作调度和 Distributed runtime；这些能力由后续 Feature 处理
- MVP 默认提供单机本地沙箱能力，并为云沙箱或容器化后端保留扩展边界
- 沙箱必须优先保证“显式失败”而非“隐式降级”；隔离能力不可用时不自动改用普通本地执行
- Workspace、Tool、Agent、Event 和 Error 基础能力已由前序 Feature 提供，本 Feature 只定义它们与沙箱的用户可观察集成行为
- 网络默认策略采用安全优先原则：除非调用方显式允许，否则沙箱网络访问应被禁用或受限
- 执行历史用于调试和兼容性报告，不记录敏感环境变量的明文值
- 与 Python AgentScope 的 sandbox/workspace 能力以可观察行为兼容为目标；宿主平台差异导致的不可兼容必须登记
