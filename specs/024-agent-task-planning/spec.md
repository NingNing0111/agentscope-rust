# Feature Specification: Agent 任务规划重构（内置任务规划工具）

**Feature Branch**: `024-agent-task-planning`

**Created**: 2026-08-03

**Status**: Draft

**Input**: User description: "参考python版本的agentscope，重构下当前rust版本的agent，不需要实现planneragent，原项目是通过内置和实现 任务规划工具 实现的。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 通过内置任务工具自主规划复杂任务 (Priority: P1)

开发者使用本库构建的 Agent 收到最终用户提出的复杂多步骤请求（例如"重构这个模块并更新测试和文档"）时，Agent 能够在推理-行动循环中自主创建结构化任务清单、按依赖顺序逐项执行、实时更新任务状态，并在完成后给出最终答复。整个过程不需要开发者编写任何规划代码，也不需要配置任何独立的规划组件。

**Why this priority**: 这是本次重构的核心价值——用与 Python 参考实现一致的内置任务工具替代独立规划器，让任务规划能力成为 Agent 的默认内置能力。没有它，其余故事都没有意义。

**Independent Test**: 使用默认配置构建一个 Agent，向其提出一个需要 3 步以上才能完成的请求，观察其是否创建任务清单、逐项推进并更新状态直至全部完成，最终产出正确答复。仅此一条故事即可构成可用 MVP。

**Acceptance Scenarios**:

1. **Given** 一个默认配置的 Agent（任务工具已启用），**When** 用户提出需要 3 个或以上步骤的复杂请求，**Then** Agent 在执行过程中创建任务清单，每个任务包含标题与描述，并按合理顺序逐项执行、更新状态，全部完成后给出最终答复
2. **Given** 一个默认配置的 Agent，**When** 用户提出一个简单的一次性请求（如"这句话什么意思"），**Then** Agent 直接作答，不创建任务清单
3. **Given** Agent 已创建多个任务，**When** 模型完成其中一个任务，**Then** 该任务状态被标记为已完成，且 Agent 能查询到下一个可执行的任务
4. **Given** Agent 已创建存在依赖关系的任务（任务 B 依赖于任务 A），**When** 查询任务列表，**Then** 任务 B 被明确标示为受任务 A 阻塞，任务 A 完成前 Agent 不会开始任务 B

---

### User Story 2 - 任务状态随会话持久化并在压缩后保持感知 (Priority: P2)

开发者启用会话持久化或长对话场景下，Agent 的任务清单作为 Agent 状态的一部分被保存和恢复；当对话上下文被压缩导致任务工具的调用痕迹消失时，Agent 能收到一条提示，告知仍存在未完成的任务，从而继续推进而不是遗忘。

**Why this priority**: 任务规划的价值在长任务、多轮会话中才能体现。如果任务状态随上下文压缩或会话重启而丢失，任务清单就退化为一次性草稿，P1 的能力在真实场景中不可靠。

**Independent Test**: 创建含未完成任务的 Agent 状态，执行会话保存/加载往返，验证任务字段完整无损；模拟上下文压缩后触发一次回复，验证 Agent 收到未完成任务提醒并继续执行。

**Acceptance Scenarios**:

1. **Given** Agent 的任务清单中存在未完成任务，**When** 会话被保存后重新加载，**Then** 所有任务字段（标识、标题、描述、状态、依赖、负责人、元数据、创建时间）完整恢复
2. **Given** Agent 存在未完成任务，且上下文中任务工具的调用痕迹已被压缩移除，**When** Agent 开始新一轮推理，**Then** 其上下文中被注入一条提醒，说明进行中与待处理任务的数量，并指引其查看任务清单
3. **Given** Agent 上下文中仍存在任务工具的调用痕迹（Agent 已感知任务），**When** 新一轮推理开始，**Then** 不重复注入任务提醒，避免每轮冗余提示
4. **Given** 所有任务均已完成，**When** 发生上下文压缩，**Then** 不注入任何任务提醒

---

### User Story 3 - 移除独立规划器，统一规划能力入口 (Priority: P3)

开发者不再需要学习、配置或维护一个独立的规划器（Planner）组件及其专属的配置、错误类型、事件流与追踪结构。任务规划能力统一通过工具系统暴露，与其他工具遵循相同的注册、权限、流式事件与中间件机制。库公开 API 中不再存在独立的规划器类型。

**Why this priority**: 这是重构的"减法"部分，降低 API 表面积与认知负担，但它依赖于 P1/P2 提供等效能力后才能安全落地，因此优先级靠后。

**Independent Test**: 检查库的公开 API 与文档，确认不存在独立的规划器入口；使用默认 Agent 即可完成 P1 的全部验收场景。

**Acceptance Scenarios**:

1. **Given** 开发者查阅库的公开 API，**When** 搜索任务规划相关能力，**Then** 规划能力仅通过内置任务工具呈现，不存在独立的规划器配置、错误类型或事件类型
2. **Given** 一个使用默认配置构建的 Agent，**When** 完成 P1 的全部验收场景，**Then** 无需任何规划器相关配置
3. **Given** 既有示例与文档，**When** 开发者阅读任务规划相关内容，**Then** 所有示例均基于内置任务工具，不存在已移除组件的引用

---

### Edge Cases

- 模型尝试更新或查看不存在的任务标识时，系统返回明确的错误结果供模型自我纠正，推理循环不中断
- 任务被删除时，其他任务对它的依赖引用（blocks / blockedBy）被自动清理，不留悬空引用
- 模型尝试建立依赖关系时引用了不存在的任务标识，该引用被忽略且不影响其他有效字段的更新
- 任务清单为空时，查询任务列表返回明确的"无任务"提示而非错误或空白
- 任务工具被配置禁用后，Agent 不注册这些工具，也不注入任务提醒，行为退化为纯推理-行动循环
- 回复过程被中断时，已创建的任务状态保持中断时刻的一致状态，恢复会话后可继续推进
- 模型以非法状态值更新任务时，返回校验错误而非静默接受

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Agent 必须内置一组任务管理工具，供模型在推理-行动循环中调用，覆盖任务的创建、列表查询、详情查询与更新四类操作，且工具命名、行为与 Python 参考实现（TaskCreate / TaskList / TaskGet / TaskUpdate）保持一致
- **FR-002**: 每个任务必须包含以下属性：唯一且按数值递增的顺序标识、标题（subject）、详细描述（description）、状态（pending / in_progress / completed）、负责人（owner，可为空）、阻塞关系（blocks / blockedBy 双向引用）、任意键值元数据（metadata）、创建时间
- **FR-003**: 任务创建时必须初始为 pending 状态，且新任务标识在当前任务集合的最大数值标识基础上递增；历史遗留的非数值标识不参与递增计算
- **FR-004**: 任务更新必须支持：修改标题、描述、负责人、状态；追加阻塞关系（add_blocks / add_blocked_by）；合并或删除元数据键（值为 null 时删除该键）
- **FR-005**: 阻塞关系必须双向一致——为任务 A 添加"被 B 阻塞"时，任务 B 的 blocks 列表必须同步包含 A；建立依赖时引用不存在的任务标识必须被忽略
- **FR-006**: 任务状态流转必须支持 pending → in_progress → completed，并支持通过删除状态永久移除任务；删除任务时必须自动清理所有其他任务对它的 blocks / blockedBy 引用
- **FR-007**: 任务集合必须作为 Agent 状态的一部分存储，随会话保存/加载完整往返，且在上下文压缩后仍然保留（任务不存放于可被压缩的对话上下文中）
- **FR-008**: 当存在未完成任务（pending 或 in_progress）且当前对话上下文中既没有任务工具调用痕迹、也没有先前的任务提醒时，系统必须向对话上下文注入一条提醒，说明进行中与待处理任务的数量，并指引模型查看任务清单；当 Agent 已感知任务或无未完成任务时不得注入
- **FR-009**: 任务提醒必须以非系统提示词的方式注入对话上下文（如提示块），不得修改系统提示词，以保证提示缓存继续有效；注入内容必须可通过固定来源标识在上下文中被识别，用于感知检测
- **FR-010**: 任务工具必须在 Agent 默认配置下自动注册到工具集，并可通过配置整体禁用；禁用后不得注册工具、不得注入任务提醒
- **FR-011**: 任务工具必须始终通过权限检查（视为安全的内部状态操作，不触发用户审批），且其调用与结果必须复用现有工具事件与流式管线，与其他工具行为一致
- **FR-012**: 任务工具的描述必须引导模型在复杂多步骤场景主动创建任务、在琐碎场景避免创建任务，并说明状态流转纪律（完成才标记 completed、阻塞时保持 in_progress 并创建新任务描述阻塞原因等）
- **FR-013**: 任务工具的异常输入（不存在的任务标识、非法状态值、缺失必填字段）必须返回结构化错误结果供模型纠正，不得导致推理循环崩溃或 Agent 状态损坏
- **FR-014**: 库公开 API 中必须移除独立规划器组件及其专属的配置、错误类型、事件流与追踪结构；既有引用该组件的示例、文档与集成测试必须迁移到内置任务工具或移除

### Key Entities *(include if feature involves data)*

- **Task（任务）**: Agent 会话内的一条工作项，包含顺序标识、标题、描述、状态、负责人、双向阻塞关系、元数据与创建时间；生命周期为 pending → in_progress → completed，或被永久删除
- **TaskContext（任务上下文）**: Agent 状态内保存任务集合的容器，随 Agent 状态一起持久化，与可被压缩的对话上下文相互独立
- **Task Tools（任务工具）**: 注册到工具集的内置工具集合（创建/列表/详情/更新），以 Agent 状态为操作对象，是模型与任务上下文交互的唯一入口

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在需要 3 步以上的复杂请求评测场景中，Agent 无需开发者编写任何规划代码即可完成任务清单的创建、执行与收尾，端到端成功率达到 100%（基于仓库内置评测/集成测试场景）
- **SC-002**: 会话保存/加载往返后，任务的所有字段（标识、标题、描述、状态、负责人、双向依赖、元数据、创建时间）100% 保留
- **SC-003**: 上下文压缩移除任务工具调用痕迹后，Agent 在下一轮推理中收到未完成任务提醒的比例为 100%；已感知任务或无未完成任务时提醒注入次数为 0
- **SC-004**: 开发者使用默认配置即可获得任务规划能力，所需的额外配置项为 0；禁用任务工具所需的配置项不超过 1 个
- **SC-005**: 任务工具的错误输入（不存在的标识、非法状态、缺失字段）100% 以结构化错误结果返回，推理循环零崩溃
- **SC-006**: 重构后公开 API 中独立规划器相关类型数量为 0，且除被移除的规划器路径外，其余既有测试全部通过

## Assumptions

- 用户已明确不需要 PlannerAgent，因此完全移除独立规划器（破坏性变更）是可接受的；本项目处于 1.0 之前的快速演进期，不为旧规划器 API 保留兼容层
- 工具命名与 Python 参考实现保持一致（TaskCreate / TaskList / TaskGet / TaskUpdate），以降低跨语言使用者的认知成本并保持文档一致性
- Python 参考实现的运行时状态注入还包含时间与上下文用量两个维度；本特性仅落地任务维度，时间与上下文用量维度如需支持将作为后续独立特性
- 任务工具的启用默认为开启（与"规划是内置能力"的定位一致），通过配置可整体禁用
- 任务的负责人（owner）字段用于多 Agent 协作场景的任务认领，但跨 Agent 共享任务看板不在本特性范围内
- Python 参考实现中的计划提示模板（system-reminder 包裹格式）作为注入内容的默认样式参考，允许在实现时按本库消息模型适配
- 任务工具产生的提示注入事件复用现有事件管线，是否对外暴露独立的提示事件类型由实现阶段决定，不作为验收门槛
